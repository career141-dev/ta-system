## 1. Question

Does a cheap hosted model, using the evidence-quote screen (prompt v3), do better than the free laptop model on **the identical frozen inputs**, judged against the recruiter's 120 existing decisions (development jobs 4, 9, 12)?

**A good result can justify:** labelling the development manifests and running P2.

**It can't show:**
- readiness
- the 90% retention gate (15 of 18 kept is 83.3%)
- 90–95% suitability

These 120 people were used to write the screening rules: they are development data.

## 5. Safeguards (`lib/p1Runner.ts`, `lib/runLedger.ts`, `lib/screenAnswer.ts`)

### 5.1 Before sending

| Check | Behaviour |
|---|---|
| Approval | Must equal `<manifest hash>:<runner hash>`; dedicated key present and not the platform key; `--cap` matches the manifest |
| Request integrity | Every request's hash, including candidate and job ids, must match the manifest, one-to-one; otherwise nothing is sent |
| Ledger contents | Every record is validated on opening and before each append: known type, exact fields, finite non-negative amounts, unique reservations, settlements and reconciliations only for existing reservations and only once, a resolution only after a halt, the opening record matching run, allowance, manifest and runner. A partial last line, unreadable line, missing ledger after start, or any invalid record stops the run without rewriting history |
| Halt | An unresolved halt in the ledger means no reservation is accepted, so nothing is sent, including after a restart |
| Reservation | Written and flushed to disk before the request. If committed spend plus this reservation would pass the allowance: stop, rest `not_run` |
| Concurrency | Exclusive lock; a second runner is refused; a stale lock is removed only by a person |

### 5.2 After each response

| Situation | Behaviour |
|---|---|
| Confirmed charge above **that attempt's own reservation** | Recorded at the actual figure; a halt is written; nothing further is sent, including after restart, until a person records a resolution with an approval reference |
| Reported input tokens above the frozen token bound | Halt, same rules (the reservation assumption is broken) |
| No response | Uncertain, held at the reservation; one retry, reserved separately |
| HTTP error | Uncertain, held at the reservation; not retried |
| No reported cost | Uncertain, held at the reservation |
| Three failed requests in a row | Stop |
| Answer fails the v3 schema (`{}`, unknown decision, missing gate or field, non-JSON) | `invalid_output`, never `ok` |
| Answer cut off at 600 tokens | `truncated` |
| Valid answer with a missing or unfound evidence quote, or a gate/decision contradiction | Kept as `ok` with **flags**; never repaired |
| Process killed mid-request | Lock left; after a person removes it, the interrupted request is not resent (`no_response`, held at maximum) |

### 5.3 Final report (`final.json`)

- One row per manifest request, in manifest order, with no omissions or duplicates. A row is either the result, or `not_run` with the stop reason.
- Each row lists every ledger attempt and the request's total across attempts, so a retried request counts both.
- The attempt history (`results.jsonl`) and the ledger are kept separately.
- Uncertain charges are reconciled afterwards against OpenRouter's generation record, and stay at their reservation until then.

## 6. Cost

| | DeepSeek V4.1 Flash | GLM 5.3 Flash | Total |
|---|---:|---:|---:|
| **Expected** (characters ÷ 4 input tokens, 300 output tokens; an estimate) | $0.110 | $0.084 | **$0.194** (≈ $0.204 with the credit fee) |
| Sum of reservations (input ≤ UTF-8 bytes + 64 chat tokens; all 600 output tokens) | $0.399 | $0.303 | $0.701 |

**What the numbers mean:**
- **The expected figure is an estimate.** The real charge is recorded per request.
- **The reservation bound is not a guaranteed maximum.** It assumes byte-level tokenizers, which both models are believed to use but which isn't verified here. Any request reporting more input tokens than the bound halts the run. The bound also doesn't cover provider-side charges outside tokens.
- **Retries and uncertain charges** each hold a full reservation.
- **Allowance: $0.40 of provider usage**, enforced by the ledger.
  - With confirmed costs, committed spend stays near actual cost, so the $0.70 reservation total doesn't stop a normal run. The normal dry run finished at $0.193.
  - If the provider reports no costs, reservations reach the allowance after about 60% of requests. The comparison is then incomplete, with both models covered evenly.
- **What is protected, and what isn't.** Spending is stopped before any request whose reservation would pass $0.40. A stop after a charge can't undo that charge: a single request charged above its reservation can take actual spend past $0.40 before the halt.
- **The outer limit is the dedicated key's $0.50 spending limit, enforced by OpenRouter.**
- **A larger allowance, or resuming after a halt, needs a new approval.**

## 7. Evaluation and the continue rule (`lib/p1Evaluate.ts`)

**Reported per model, per job and overall, beside the laptop baseline on the same inputs:**
- model Shortlist, and how many of those the recruiter shortlisted, or shortlisted or maybe'd
- model Shortlist + Maybe, and the share acceptable
- recruiter Shortlists kept; recruiter Shortlist + Maybe kept
- false rejects, listed by id
- invalid, truncated, failed and not-run counts
- answers with consistency flags
- ledger cost, with uncertain requests counted
- share routed to a second look under the frozen routing rule

**Continue rule, computed in code:**

| Verdict | When |
|---|---|
| **continue** | Full coverage (no request not run or failed) **and** ≥ 15 of the 18 recruiter Shortlist + Maybe kept **and** ≤ 36 put forward **and** ≤ 5 invalid or truncated |
| **stop** | Full coverage and a condition missed; or the bar is missed even if every unanswered person went the model's way |
| **inconclusive** | Incomplete coverage where the result could go either way. It never passes, even if 15 are already kept |

A continue justifies development labelling and P2 only. No automatic escalation.
